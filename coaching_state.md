#### S009 — ECR Incident + Alert Redesign
- Situation: The ECR team was experiencing a high volume of monthly Level 5 incidents. Every month, the WECR guardrail was being triggered — requiring L7 approval to stop payouts, waking engineers in the middle of the night to manually halt them. This was painful, unfair (random which drivers got stopped), and didn't actually solve the original problem (reducing screenshot risk and preventing take rates above 30% of rider fare).
- Task: Reduce incident frequency, design a better alert system, and kick off a longer-term platform migration to address the underlying architecture limitation.
- Action: Diagnosed root causes of each incident category: (1) marketplace pricing changes, (2) natural business growth, (3) bugs (e.g., fraud reversals). Key insight: most incidents were "intended" in the sense that ops had set absolute thresholds that would predictably trigger at scale — not a bug, a design flaw. Stop pays weren't a solution — they were random, unfair, and didn't address the core problem. Built a two-threshold alert architecture: (1) Relative threshold — daily query comparing cumulative WECR spend this week vs. last week. Doesn't create an incident, but alerts ops + eng to potential anomalies in advance. Catches problems before they become L5s. (2) Absolute "kill switch" — set much higher, only triggers for genuine bugs or unintended large overspend. Also kicked off conversations to migrate to a new platform. The underlying issue: SIP only calculates ECR once per week — no infrastructure to track cumulative guardrail spend in real-time. Manual daily queries can't catch weekend overspend before it happens. A platform with real-time tracking would enable accurate, timely alerts and eliminate the need for manual intervention.
- Result: No false positive alerts since implementation. No WECR overspend since the new system went live. Platform migration currently in progress.
- Earned Secret: Stop pays feel like control but they're actually chaos — random, unfair, and treating the symptom while leaving the root cause intact. The real problem was operating reactively on weekly batch data. Solving reliability isn't about adding more alarms; it's about redesigning the feedback loop so the team is never surprised.
- Deploy for: System reliability, incident root cause diagnosis, proactive vs. reactive engineering thinking, PM-EM partnership in technical problem-solving, data infrastructure and platform migration judgment
